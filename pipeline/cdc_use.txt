Configurations les plus courantes :

1) Chargement complet : annule/remplace
Les données de la table persistante sont supprimées et remplacées par celle de la table de staging.

config_json = """{
    "staging_area" : {
        "table" :         {"schema" : "nx_staging",  "name" : "AAA_test_pbx"},
        "view" :          {"schema" : "nx_staging",  "name" : "v_AAA_test_pbx"}
    },
    "persistent_area" : {
        "table" :         {"schema" : "nx_business", "name" : "AAA_test_pbx"},
        "view" :          {"schema" : "dbo",         "name" : "AAA_test_pbx"}
    },
    "mapping" : [
        {"position" :  1, "persistent_column" : "id",   "staging_column_or_expression" : "id"},
        {"position" :  2, "persistent_column" : "col1", "staging_column_or_expression" : "col1"},
        {"position" :  3, "persistent_column" : "col2", "staging_column_or_expression" : "col2"}
    ],
    "sync" : {
        "mode" : "append",
        "action_on_table" : {
            "delete_rows" : true
        }
    }
}"""

Remarques :
- Si la volumétrie est importante et que l'on accepte que les données ne soient pas en ligne pendant la durée du chargement, on peut remplacer "delete_rows" : true par "truncate" : true
- Les configurations de type "Chargement complet" sont à éviter si la volumétrie est élevée (risque de saturation des journaux de transactions, copie inutile de données dans la table de staging).

2) Chargement complet : annule/remplace sur un périmètre restreint
La table de staging ne contient qu'une partie des données de la table concernée (lignes créées depuis 1 an par exemple).
Les données de la table persistante sont supprimées sur le même périmètre et remplacées par celle de la table de staging.

        }
    }
}"""

Les changements opérés sur données de la table de staging par rapport à celles de la table persistante sont répercutés dans la table persistante.

5) Chargement incrémental : propagation des ajouts et des modifications
Les ajouts et modifications opérés sur données de la table de staging par rapport à celles de la table persistante sont répercutés dans la table persistante.
Les suppressions ne sont pas prises en compte, cette configuration est donc à privilégier si les données ne sont jamais supprimées physiquement de la table concernée.
La table de staging peut ne contenir que les lignes créées ou modifiées depuis le dernier chargement (ou avant).

- Bloc "staging_area" : entités de la zone de staging.
    - table : table de staging contenant les données à propager
    - pk_table : table de staging contenant uniquement les identifiants des lignes afin de permettre la detection des suppressions lors d'un chargement incrémental
    - view : vue appliquant les règles du mapping (expressions SQL, type des colonnes, distinct) à la table de staging
    - cdc_table : table dans laquelle sont enregistrées les changements détectés
    Pour chaque entité, on définit:
        - schema : son schéma dans la base de données
        - name : son nom dans la base de données
- Bloc "persistent_area" : entités de la zone de persistance.
    - table : table persistante
    - history_table : table de stockage des données historiques (SCD4 uniquement)
    - view : vue de présentation des lignes actives de la table persistante masquant les colonnes techniques
- Bloc "mapping" : mapping des colonnes entre la table de staging et la table persistante
    - position : position de la colonne dans la table persistante. La position doit être unique dans la table. Elle est utilisée pour trier les colonnes lors du calcul des hashes, elle ne doit donc pas être modifiée.
    - persistent_column : nom de la colonne dans la table persistante
    - staging_column_or_expression : nom de la colonne dans la table de stagin ou expession SQL permettant son calcul.
    - datatype : type de la colonne dans le SGBD (INT, CHAR, DATE, ...). S'il n'est pas précisé, il est détecté automatiquement.
    - is_pk : indique si la colonne fait partie de la PK. Par PK, on entend identifiant unique des lignes, elle n'a pas besoin d'être déclarée explicitement dans la base de données.
    - use_for_cdc : indique si la colonne est utilisée dans le calcul du hash de la ligne. D'une manière générale, on exclut les colonnes de la PK et les colonnes d'audit (en particulier la date de dernière modification)
- Bloc "sync" : paramètres de synchronisation des données
    - mode : mode de synchronisation (append/scd1/scd2/scd3/scd4)
    - Bloc "action_on_table" : actions sur la table en mode append uniquement
        - truncate : tronque la table
        - delete_rows : supprime des lignes de la table
        - delete_rows_condition : condition de supression de lignes de la table. Ignoré si "delete_rows" : false. Si non renseigné, toutes les lignes sont supprimées.
    - persistent_table_filter_expression : expession SQL du filtre appliqué sur les lignes de la table persistante lors de la CDC
    - Bloc "deleted_rows" : gestion des suppressions en mode SCD
        - ignore : ne prend pas en compte les suppressions de lignes si vrai
        - soft_delete : si vrai les suppressions sont gérées de manière logique (flag indiquant que la ligne est inactive, date de fin de validité)
        - use_pk_table : utilise la table de staging contenant uniquement les identifiants des lignes pour détecter les suppressions
    - Bloc "technical_columns" : colonnes techniques à crée
        - pk_hash : hash SHA2-256 des colonnes de la PK. Obligatoire en mode SCD.
        - row_hash : hash MD5 des colonnes de la CDC. Obligatoire en mode SCD.
        - first_change_date : date de création de la ligne en mode SCD1, date de début de validité de la ligne en mode SCD2 ou 4
        - last_change_date : date de dernière modification de la ligne en mode SCD1, date de fin de validité en mode SCD2 ou 4
        - is_active : indique que la ligne est active
    - distinct_rows : indique que les lignes de la table de staging doivent être sélectionnées avec le mot clé DISTINCT
    - end_of_time_is_null : si vrai, la date de fin de validité des lignes actives est NULL. sinon elle vaut "9999-12-31 23:59:59"
